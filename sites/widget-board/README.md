# Widget Board on Sites

Private remote MCP and board storage for the native Widget Board prototype.

- `/mcp`: stateless MCP JSON-RPC. Supports Sites discovery (`2026-07-28`) and legacy initialization (`2025-11-25`, `2025-06-18`, `2025-03-26`).
- Tools: `get_examples`, `get_board` and `set_board`, for one canvas per account. `get_examples` returns the approved designs as complete specs for an agent to adapt; it reads no user data.
- `GET /boards`: list the signed-in user's boards.
- `GET /boards/:id`: read `{ id, spec, updatedAt }`, matching the Swift model.
- `PUT /boards/:id`: validate and replace a board with `{ spec }`.
- `/`: responsive board preview and note composer.

## Authentication and storage

Sites dispatch handles ChatGPT sign-in, MCP authentication, and the private audience. Application code requires the dispatch-injected `oai-authenticated-user-id` for every board read and write. The D1 primary key is `(owner_id, id)`. Caller arguments never select the owner. The MCP discovery responses contain only tool metadata and remain identity-independent for Sites plugin provisioning.

Do not expose this Worker directly outside Sites: its identity headers are trusted only behind Sites dispatch. A Sites service-access token does not supply user identity, so it cannot read or write personal boards. The read-only device routes separately verify a revocable device token. No credential is embedded in the app binary or a browser bundle.

JSON requests are limited to 32 KB; specs to 64 elements and 8 levels. The existing native component catalog validates props; extra validation rejects cycles, repeated children, orphaned elements, and missing references. Private responses use `Cache-Control: private, no-store`. Browser writes reject foreign origins.

## Local development

Requires Node 22.13+. From a fresh clone, run `npm run setup`, then
`npm run install:ci`. The setup creates an ignored hosting manifest without a
Site ID and preserves existing configuration.

```sh
npm run typecheck
npm test
npm run db:generate   # only after changing db/schema.ts
npm run build
```

Build once, then apply every SQL migration in `drizzle/` in filename order before preview.
For example, the first migration is:

```sh
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_lumpy_mindworm.sql
npm run dev -- --host 127.0.0.1 --port 4750
```

The starter supplies a simulated local identity. This tests the UI and local D1; it does not verify hosted ChatGPT sign-in. Local and hosted data are separate. Sites applies tracked migrations on publication.

`lib/catalog/` is a checked-in snapshot of `server/src/catalog.ts` and `server/src/spec.ts` from the containing widget-board repository. After changing the native component contract, run `node scripts/sync-sites-catalog.mjs` from that repository's root. The Site's standalone source repository builds without needing the containing project.

## Publication and connection

For a new deployment, create your own Site with the Sites tooling and store its returned
project ID in `.openai/hosting.json`. Once a Site is configured, reuse its ID. The real
manifest is local and ignored by Git; it is not included in this public repository.
Follow the Sites skill to synchronize source, build, package, and publish privately. Publishing the `mcp` capability provisions a personal plugin in ChatGPT/Codex. Install/connect that plugin when prompted; no separate OAuth server or local MCP entry is required.

The parent repository keeps this directory as ordinary source files. Publication can use an isolated copy outside the parent repository so the Sites helper's Git repository does not become an embedded Git repository here. Always copy the complete source, build that exact copy, and pass the helper's returned commit and archive to deployment.

## Native iPhone connection

The iOS app uses `ASWebAuthenticationSession` to open `/device/connect`. Sites performs ChatGPT sign-in, and the user approves read-only access. A P-256 public key and fresh state are generated by the phone for each attempt. After approval, the server encrypts the connection to that public key using ECDH, HKDF-SHA256, and AES-256-GCM, with state as authenticated data. The `widgetboard://connect` callback contains only ciphertext and public cryptographic parameters. The private key stays in the app for that attempt.

The encrypted connection contains two credentials: Sites service access to pass the private hosting gate, and a random 256-bit device token that grants read-only access to the signed-in user's boards. The server stores only the device token's SHA-256 hash. Pairing is valid for 90 days. `/device/boards` and `/device/boards/:id` require the device token; MCP and ordinary browser board routes still require a Sites user identity. Device credentials cannot write boards. `/devices` lets the signed-in owner revoke individual connections. `/device/disconnect` revokes the current device.

The server needs the secret runtime variable `DEVICE_GATEWAY_TOKEN`, configured through Sites from its supported service-access credential. Do not write this value to source, local env files, browser code, logs, or documentation. Rotating the Site's service credential requires updating that runtime secret and reconnecting existing devices. The app receives it only inside the encrypted pairing response and stores it in a shared, device-only Keychain item. The native HTTP client refuses redirects so credentials are never forwarded to another host.

Both iOS targets share `group.dev.widgetboard.shared` and the signing-team-prefixed `dev.widgetboard.shared` Keychain access group. Widgets fetch the hosted API and can show the last successfully fetched board during transient network failures. An authentication rejection clears the device connection and cache. The prototype's local data is not uploaded automatically.

The transport includes legacy MCP initialization, but Claude's authentication against Sites remains unverified. WidgetKit refresh timing is controlled by iOS.

## Widget push updates

On iOS 26+, the native app and widget register a WidgetKit push token with `PUT /device/push`, authenticated by the existing device credential. Registrations include the signed APNs environment and whether a Board widget is present. Reconnecting a phone moves that token off its old connection. Revoked and expired connections are excluded from delivery.

Every successful board save requests a silent WidgetKit refresh for that owner's devices displaying the changed board. APNs receives only `{ "aps": { "content-changed": true } }`, never board content. Requests use the `widgets` push type and `dev.widgetboard.app.push-type.widgets` topic, coalesce pending refreshes, and time out after five seconds. Invalid tokens are removed; temporary failures retain the registration. A push failure does not roll back the board save.

Configure `APNS_TEAM_ID`, `APNS_KEY_ID`, and `APNS_PRIVATE_KEY` through Sites runtime secrets. The private key must be an Apple APNs P-256 `.p8` signing key authorized for `dev.widgetboard.app` and the device's environment. Never commit it or put it in frontend code. A sandbox-only key covers Xcode development installs; App Store/TestFlight delivery requires a production-authorized key. Until configured, saves report `push.status: "not_configured"` and normal polling continues.

The save response distinguishes `accepted`, `partial`, `failed`, `not_configured`, and `no_devices`. `accepted` proves APNs accepted the refresh request, not that the phone rendered it. WidgetKit budgets and schedules push delivery. The existing 15-minute timeline request remains the fallback. Open the native app once after installing push support to register the existing Home Screen widgets.

## Widget presentation

Small shows the first content leaf. Medium adds the next two in a supporting column.
Rows preserve content order instead of forcing additional rows into a small widget.
The full canvas remains available under View all details and in the iPhone app.
Keep the headline first and make its units and time period explicit; a canvas save
is not evidence of a new source sync. The tool reference includes these guidelines.

A Stat shows its label, styled value, and optional `supportingText` on both widget sizes.
Use that supporting field for a short comparison rather than a separate Note. Container
titles, captions, and save timestamps remain available in details.
